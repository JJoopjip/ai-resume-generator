Split the brain from the machine.

Give it a job posting; a few minutes later you have a polished, one-page résumé — PDF and Word — tailored to that exact role. The interesting part isn't that an AI writes it. It's the architecture around the AI: a pipeline where judgment and exactness are kept strictly apart, and where the model is put on a leash it can't slip.

01 · Architecture

Two halves, one contract.

The AI does the fuzzy, context-dependent work only it can do well. Plain, deterministic software does everything that must be exact and repeatable — and no AI runs inside that half at all. They hand off through a single, unambiguous interface.

02 · The self-correcting loop

The AI drives the loop — and reacts to the verdict.

Control flows in one direction: the launcher only starts the agent; the renderer never calls back into it. Within that, the agent runs its own feedback loop against the machine's verdict.

STATE A

Draft

The agent writes a candidate résumé — its selections, in priority order.

STATE B

Render

It calls the deterministic renderer and reads the exit code.

STATE C

Verdict

Pass, reject, or overflow — a number, not prose to interpret.

STATE D

React

It fixes or trims accordingly, then renders again — capped at 5 attempts.

Fits on one page Finished draft. Stop.
exit 0
Too long Drop the lowest-priority bullet the AI ranked, retry.
exit 3
A fact drifted Rejected. The AI repairs the exact field named, retry.
exit 1

03 · Trust

Two kinds of “accuracy” — measured separately.

“Is this résumé accurate?” is really two questions. The pipeline answers each with its own tool, on purpose: one is a hard gate, the other an advisory signal.

Truthfulness · enforced

Is every fact real?

Not estimated — guaranteed.

Every number, title, date, and bullet is checked character-for-character against the master record. The AI can select and reorder facts, but is mechanically blocked from rewriting them. If it drifts, the build is refused before anything renders.

05 · How it was built

I’m not a developer by trade. I wrote the specs in plain English, then directed an AI to build to them — so the specs are as much the work as the code.

The whole system was built through spec-driven development: think it through in writing first, then orchestrate the build. Both specs live in the repo — they show how a fuzzy goal gets broken down into something an AI can build reliably.

PRD.md

The product spec

What the tool is for and why — the pipeline, the schema, the rules, in plain language.

TECH_SPEC.md

The technical spec

Every implementation decision written down before the code, so the build never had to guess.

The output is always a draft for a human to review. Nothing is ever submitted anywhere automatically — the pipeline’s job is to do the judgment-heavy first pass, fast and honestly.
